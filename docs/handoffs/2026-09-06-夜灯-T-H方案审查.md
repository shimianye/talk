## 1. 当前前端 API 调用链

```
Chat.tsx::send()
  └─ api.chat(message, sessionId)                 [frontend/src/api.ts:53]
       └─ request() → fetch POST /api/v1/chat      [同步 JSON，非流式]
            └─ 后端 handle_chat() 同步跑完整个 Agent 图
            └─ 返回完整 JSON { answer, intent, handoff_required, guardrail_flags, mode }
       └─ res.json() 一次性解析
  └─ setMessages 一次性追加完整 answer             [Chat.tsx:25]
```

特征：
- **纯同步请求**：前端 `await` 完整答案后才渲染，无任何流式消费。
- 前端**没有** `EventSource` / `ReadableStream` / `getReader` 等流式代码（已全仓 grep 确认）。
- 唯一调用点：`Chat.tsx:23`。`Console.tsx`（客服控制台）走的是 admin 接口，不涉及 chat。
- `loading` 期间仅显示「正在思考…」占位气泡。

## 2. 后端 SSE 接口现状

`POST /api/v1/chat/stream` **已实现**（`backend/app/api/routes/chat.py:46`），事件序列：

```
status          → {"message":"正在思考…"}
message_start   → 元数据（conversation_id / intent / pending_confirmation / handoff_required / mode，不含 answer）
token           → 单个字符（逐字）
message_end     → {"answer": 完整答案}
done            → {}
```

- 用 `StreamingResponse` + `text/event-stream`，已带 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`。
- **⚠️ 关键：这是「伪流式」**。`handle_chat()` 是同步的——先 `await run_turn()` 跑完整个 LangGraph 图、拿到完整 `final_answer`，之后才在 `event_stream()` 里按字符 `yield`。
- **LLM 层没有真流式**：`LLMClient` 抽象只有 `complete` / `complete_json`（`llm/base.py`），`LLMResponse` 是完整响应，无 `stream` 方法。DeepSeek 客户端也未接 `stream=True`。

结论：**后端接口已就位，前端可以直接消费；但首字延迟与同步版相同（LLM 仍是完整生成后才返回）**。要真正降低首字延迟，得动 LLM 层 + LangGraph 流式，属另一档改造。

## 3. T-H 实施范围

**前端（核心，后端不用动）：**

1. `frontend/src/api.ts`：新增流式聊天封装。
   - 因为要 **POST + 携带 `Authorization` 头**，**不能用 `EventSource`**（它只支持 GET、无法自定义 header），必须用 `fetch` + `response.body.getReader()` + 手动解析 SSE 帧（按 `\n\n` 切分，解析 `event:` / `data:` 字段）。
2. `frontend/src/pages/Chat.tsx`：`send()` 改为消费流：
   - 收到 `status` → 显示「正在思考…」
   - 收到 `message_start` → 创建 agent 气泡，写入 `session_id` / `intent` / `handoff` 等元数据
   - 收到 `token` → 逐字追加到当前气泡（打字机效果）
   - 收到 `message_end` / `done` → 收尾、复位 loading
   - 异常/中断处理：`reader.cancel()`、AbortController、错误气泡

**后端：本轮不改**。现有 `/chat/stream` 已满足「前端流式消费」目标。

**边界外（建议单列，不混入 T-H）：**
- 真 token 级流式：LLM 层加 `stream` + LangGraph `astream` + 工具调用循环流式。改动面大，建议归入 T-L（决策文档 v2 补 SSE 章节）一并评估，或独立任务。

## 4. 风险与验收标准

**风险：**

| # | 风险 | 应对 |
|---|------|------|
| 1 | `EventSource` 不支持 POST+Header | 用 `fetch` + `ReadableStream` 手动解析 SSE，注意帧的 `\n\n` 分隔与 `event`/`data` 字段 |
| 2 | 伪流式：前端逐字渲染但首字延迟不变 | 若目标是「降低首字等待」，仅改前端不够，需后端真流式；本轮目标应是「打字机视觉体验」，需在方案里明确 |
| 3 | 单字符 `token` 太碎，渲染性能/抖动 | 可前端做小批量合并渲染（如每 16ms 或每 N 字符 flush 一次），或后端改按词推送 |
| 4 | 代理/nginx 对 SSE 缓冲 | 后端已带 `X-Accel-Buffering: no`；前端 fetch 需确保不缓存 |
| 5 | 流中断与会话一致性 | 后端是完整生成后统一 `commit`，前端中断不影响已存数据，但前端要有重试/恢复与错误气泡 |

**验收标准：**

- 聊天页逐字渲染（打字机效果），`message_start` 后即出现气泡
- 转人工 / 确认 / 错误 状态正确显示（`handoff_required`、`pending_confirmation` 与同步版一致）
- 多轮会话、确认恢复行为与 `/chat` 同步版一致
- 流正确关闭，无内存泄漏、无重复渲染
- 45 测试全绿（前端改动不触碰后端测试）
