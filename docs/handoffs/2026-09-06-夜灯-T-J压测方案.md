# 交接 · 2026-09-06 · 夜灯 → T-J 20 并发压测方案审查

> 只读方案建议,未改代码。基准:本地 `b407fbf`(T-I 已闭环)。

## 现状

- 仓库**无任何压测脚本/工具**(仅 node_modules 里误命中)。
- `GET /api/v1/health` 是轻量占位(不碰 DB/LLM),**不适合**作为压测对象。
- 核心业务接口 `POST /api/v1/chat` 需 Bearer JWT(`get_current_user`,sub=user_id)。
- 沙箱无 docker/数据库,**压测需失眠夜本机做**(与截图同理)。

## 压测对象:建议 `POST /api/v1/chat`

理由:它跑完整 Agent 图(意图提取 → 工具调用 → LLM → DB 写 Message/AgentTrace/AuditLog → commit),是真实用户路径;压它才有说服力。压 `health` 只能证明「框架能扛」,不能证明「客服能扛」。

## 工具:建议 Locust

- Python 技术栈一致、可精确统计 P50/P95、报告可读;
- 备选 `vegeta`/`hey`(Go 单二进制,简单但延迟分位统计弱)。

## 压测方案设计

| 项 | 建议 |
|----|------|
| 并发 | 20(按台账) |
| 稳态时长 | ≥60s(排除冷启动;短跑只能拿到抖动,不是 P50/P95) |
| 认证 | 先用 `U6147`/`password123` 调 `POST /auth/login` 拿 token,压测请求复用该 Bearer token |
| 请求体 | 从评测集抽 10~20 个真实问题(或硬编码),循环随机发,避免单点缓存 |
| 指标 | P50 / P95 延迟 + RPS + 错误率(按状态码分桶) |
| LLM 模式 | **必须注明** mock 还是 deepseek。mock 即时、延迟主要是 DB+Agent 图开销;deepseek 是真实网络延迟,20 并发会暴露 LLM 速率限制/排队。两者结论差异巨大,不能混为一谈 |
| 数据隔离 | 压测会写主库(Conversation/Message/AgentTrace/AuditLog),建议压独立库或压完 TRUNCATE 运行表,避免污染主库 |

## 风险与验收标准

**风险:**
1. mock 压测数字 ≠ deepseek 真实数字,结论必须标注 LLM 模式(口径红线)。
2. 压测数据污染主库 → 独立库或压完清理。
3. 压测工具与目标服务同机,资源竞争会干扰结果 → 结论注明「单机环境」。
4. 可能暴露 DB 连接池瓶颈(20 并发 × 每请求多查询),属正常发现,记入结论而非隐瞒。

**验收标准:**
- 20 并发下给出明确 P50/P95 + RPS + 错误率;
- 报告含环境指纹(commit、LLM 模式、机器配置);
- 结果写入 README 或独立报告,数字带口径。
