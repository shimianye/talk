# 手机电商智能客服 Agent：面试讲解卡

## 30 秒版本

这是一个手机零售场景的有状态客服 Agent。LangGraph 负责意图、工具调用、结果校验、用户确认和转人工；14 个工具覆盖商品、价格、库存、订单物流、知识库和售后。订单查询在 SQL/工具层校验 owner，写操作先挂起并等待用户确认，输出还会做敏感信息脱敏和高风险承诺拦截。项目用独立评测库、Alembic、CI 和固定评测集验证真实执行路径，而不是只演示聊天页面。

## 为什么它不是普通客服机器人

- 实时价格、库存和订单必须调用工具，不能靠模型记忆。
- 消费者、客服、主管和管理员看到的工具集合不同。
- 售后写操作先生成待确认动作，用户确认后才恢复执行。
- 投诉、安全事故、模型不可用和执行超限都会进入人工接管路径。
- 聊天页可展开查看经过白名单过滤的意图、工具、来源和安全状态。

## 最值得讲的产品判断

我没有向用户展示 Chain-of-Thought。它既不稳定，也可能泄露内部 Prompt、业务参数和安全策略。我展示的是可以审计的事实：系统识别了什么意图、实际调用了哪个工具、引用了哪份知识文档、触发了什么安全规则，以及对应 Trace ID。

## 最值得讲的工程问题

Agent 执行完成后会清空当前待执行 `tool_calls`，如果直接把这个字段写入 Trace，管理端看到的工具数量会一直是 0。本轮改为从真实 `tool_results` 构造执行动作快照，同时不保存参数和业务结果，兼顾可观测性与数据最小化。

## 评测怎么解释

- 100 条 Mock 评测验证的是 Agent 图、工具、数据库、安全和报告链路，不是模型能力。
- 固定 24 条求职切片用于真实模型小样本评测，样本 ID 和内容哈希在运行前固定。
- 2026-09-09 的 DeepSeek 真实切片 24/24 成功执行：意图 19/24、工具 2/4、转人工 4/5、拒答/拦截 4/6，P50 4.45 秒、P95 11.08 秒。
- Mock 和真实模型数字不能混在一起；两组样本规模与用途不同，不把差值包装成严格实验提升。
- 工具选择指标只在“期望调用工具”的样本上计算，必须同时说明分母。
- 本轮 Embedding 是 Mock；“答案产出率 100%”只说明有非空答案，不证明事实正确。

## 可直接回答的追问

- 为什么使用 LangGraph：流程包含工具循环、确认恢复、转人工和执行上限，显式状态图比自由 Agent 循环更容易测试与审计。
- 为什么要 Mock：让 CI 在没有外部 Key 时稳定验证业务链路；它不用于证明语义能力。
- 当前流式能力：后端完整生成后以字符 SSE 播放，改善阅读体验但不降低首字延迟，因此不宣称真流式。
- 下一轮先优化什么：补工具期望样本和答案事实性评分，针对漏转人工、漏拦截样本做错误分类，再优化 Prompt/规则并用独立保留集验证。
- 生产化还缺什么：真实流式模型接口、更多真实模型与真实 Embedding 评测、生产身份体系、监控告警和云环境容量验证。

## 演示顺序

1. 用消费者账号查询商品或订单，展开“AI 决策依据”。
2. 发起售后申请，展示等待确认后才能执行。
3. 输入投诉或提示词注入样例，展示拦截或转人工。
4. 切到管理员评测页，说明指标分母、失败样本和 Mock/真实模型区别。
5. 展示 CI、迁移、独立评测库和固定 24 条真实评测切片。
